# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Qué es esto

Aplicación de escritorio en Rust (Windows 11, macOS y Linux; se empieza por Windows) para convertir archivos con el mínimo esfuerzo: el usuario selecciona un archivo en el Escritorio o el Explorador, pulsa un atajo global y aparece una **paleta radial** con los formatos de destino más coherentes. Requisitos completos y decisiones abiertas: [docs/REQUERIMIENTOS.md](docs/REQUERIMIENTOS.md) — léelo antes de diseñar nada nuevo.

**Trazabilidad (obligatoria)**: [docs/BITACORA.md](docs/BITACORA.md) lleva el historial de lo hecho, el registro de decisiones (D-NN, no se borran: se marcan *Revertida*), la matriz requisito→código→pruebas y los pendientes. Al cerrar cada tanda de trabajo actualízala, diciendo qué quedó sin probar. El usuario lo pidió expresamente.

**Estado**: el core convierte imágenes (JPG, PNG, WEBP, BMP, TIFF, GIF; todos contra todos) datos (CSV, XLSX, JSON), PDF (imágenes→PDF, PDF→imágenes/TXT) y documentos de Office (DOCX/DOC/Markdown→PDF, PDF→DOCX, DOC→DOCX con LibreOffice o Word; DOCX→TXT y PDF→Markdown propios); la app Tauri ya muestra la paleta radial y funciona de extremo a extremo en Windows (atajo `Ctrl+Alt+Espacio` → lee la selección del Explorador → paleta → convierte). LibreOffice se descarga bajo demanda desde la propia paleta (Windows x64). Aún no hay OCR, HEIC, menú contextual del Explorador ni arranque con Windows. La tuerca abre un panel de **ajustes** persistentes (`settings.json`): programa de documentos (Automático/WordCraft/LibreOffice/Word) con el estado de cada uno e «Instalar» para LibreOffice, calidad JPG y WEBP, papel de los PDF (A4/Carta), resolución de PDF → imagen, atajo (solo lectura por ahora) y un hueco para el OCR. El **instalador de Windows normal pesa ~16 MiB** (58 MB en disco): la app, pdfium y **WordCraft** (el motor de documentos, D-41/D-44), sin LibreOffice; convierte todo sin internet salvo **PDF → Word**, que usa LibreOffice (se ofrece descargarlo) o Word. `scripts/build-installers.ps1 -ConLibreOffice` genera además una variante (155 MiB) con LibreOffice podado dentro y una página para elegir «Estándar» o «Con LibreOffice» (`/S /TYPE=estandar|completa`). Esa página sale de `crates/palette-app/nsis/installer.nsi`, copia de la plantilla de tauri-bundler 2.10.3 con añadidos marcados «Converter» (al subir el CLI de Tauri hay que compararla); ver [docs/DISTRIBUCION.md](docs/DISTRIBUCION.md), que recoge la estrategia por sistema y lo que está sin probar. **Plataformas**: Windows probado de extremo a extremo (también por el usuario en otro PC, instalar → usar → desinstalar); **Linux** probado en Ubuntu 22.04 (148 tests, `.deb`/`.rpm`/AppImage con WordCraft construidos, la app arranca, documentos → PDF en ~0,35 s desde el paquete) pero **sin lectura de la selección ni atajo**; **macOS compila y pasa los tests en la CI de GitHub** (los tres sistemas en verde; el release `v0.1.0` construyó los `.dmg`), pero **la app no se ha ejecutado en un Mac** y va sin firmar. El `README.md` es la puerta de entrada para usuarios; [docs/REFERENCIAS-CRAFT.md](docs/REFERENCIAS-CRAFT.md) analiza PdfCraft y WordCraft (D-38 a D-46; WordCraft, **aceptado por el usuario como motor principal**). **Decidido**: UI con **Tauri 2** (cliente fino sobre el core); multiplataforma Windows/macOS/Linux; licencia `MIT OR Apache-2.0` (sin GPL); DOCX↔PDF con Word si existe y si no LibreOffice descargado bajo demanda; OCR con **Tesseract local como proceso externo**, descargado bajo demanda. Atajo en Windows: `Ctrl+Alt+Espacio` (confirmado por el usuario). Siguen abiertos la selección de archivos y el atajo en macOS/Linux y la firma/auto-actualización (sección 8 de los requerimientos); no los des por hechos ni elijas por tu cuenta, plantéalos al usuario. Nota: la skill `grill-me` instalada solo redirige a una skill `grilling` que no existe; entrevista decisión por decisión con recomendación a mano.

## Comandos

```bash
cargo build --workspace
cargo test --workspace
cargo test -p converter-core <nombre_del_test>   # un solo test
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all
cargo build -p palette-app                       # la app: target/debug/converter.exe
cargo test -p converter-core --test office -- --ignored --test-threads=1   # tests con Word/LibreOffice (ver abajo)
cargo run -p converter-core --example convert -- <archivo> <formato> [word|libreoffice]   # convierte a mano; imprime lo escrito
cargo test -p components --test install -- --ignored --nocapture   # instala LibreOffice de verdad (374 MB, ~2 min)
powershell -File scripts/build-wordcraft.ps1    # compila wordcraft-cli v0.8.0 a vendor/bin/wordcraft (~5 min, una vez); bash scripts/build-wordcraft.sh en Linux/macOS
powershell -File scripts/build-installers.ps1   # pdfium + wordcraft-cli y el instalador normal (~16 MiB) en dist/; con -ConLibreOffice, la variante con LibreOffice y página de elección
cd crates/palette-app && CARGO_TARGET_DIR=../../target/bundle npx @tauri-apps/cli@2.12.3 build --config tauri.bundle.conf.json   # instalador NSIS en target/bundle/release/bundle/nsis (sin LibreOffice ni página de elección: falta CVT_LO_DIR; usa el script)
bash scripts/fetch-pdfium.sh                    # pdfium en Linux y macOS (el equivalente de fetch-pdfium.ps1)
cd crates/palette-app && CARGO_TARGET_DIR=../../target/bundle npx @tauri-apps/cli@2.12.3 build --config tauri.bundle.linux.conf.json   # .deb, .rpm y AppImage (en Linux); tauri.bundle.macos.conf.json para .app/.dmg (en macOS, sin probar)
cargo deny check                                # licencias y avisos de seguridad (deny.toml); cargo install cargo-deny
target/debug/converter.exe [archivo...]          # abre la paleta con esos archivos; sin args queda en la bandeja
cargo run -p os-shell --example selection -- --window <hwnd>   # prueba la lectura de selección del Explorador (--desktop para el Escritorio)
```

La interfaz (`crates/palette-app/ui/`) es HTML/CSS/JS estático **embebido en el binario al compilar** (no hay Node ni bundler): tras tocarla hay que recompilar, y con la app abierta `cargo build` falla con "Acceso denegado" (cierra `converter.exe` antes). Sin backend, `ui/index.html?demo=png|csv|empty` pinta datos de muestra en un navegador normal.

**REGLA: nunca escribas ni borres en la carpeta de datos real del usuario (`%LOCALAPPDATA%\Converter`).** El usuario instala LibreOffice de verdad desde la paleta (ahí vive `components\libreoffice-26.8.1`, ~700 MB) y guarda sus ajustes (`settings.json`). Un día esa carpeta «no existía» y a los pocos minutos sí: **comprueba su estado justo antes de tocar nada** y, para cualquier prueba, usa `CONVERTER_COMPONENTS_DIR` en `%TEMP%` (los ajustes van a `components_dir().with_file_name("settings.json")`, así que también quedan fuera). Una vez se sobrescribió su `settings.json` con datos de prueba y no se pudo recuperar (D-36). No ejecutes el desinstalador real de una instalación de prueba mientras exista su LibreOffice: el gancho (D-34) lo borra, que es justo lo que debe hacer.

**Procesos**: no cierres `converter` por nombre (`Stop-Process -Name`): cierra solo el PID del que lanzaste tú (`Start-Process -PassThru`) y mira antes si el usuario ya tiene el suyo abierto (instancia única por identificador: tu prueba se reenviaría a la suya).

**Probar la app sin molestar al usuario**: él suele tener `target/debug/converter.exe` abierto (`cargo build` falla con "Acceso denegado") y la app es de instancia única por identificador (una segunda ejecución se reenvía a la suya). Compila tu copia con `CARGO_TARGET_DIR=target/agent` y `TAURI_CONFIG='{"identifier":"dev.converter.agent"}'`, y para no instalar 1,5 GB en su perfil usa `CONVERTER_COMPONENTS_DIR` con una ruta **corta** (`%TEMP%\cvt-e2e`).

Cómo verificar la app de verdad en esta máquina (no hay tests automáticos de la ventana): lanza `converter.exe` con `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222`, evalúa JS en la página por CDP (`http://127.0.0.1:9222/json` → WebSocket → `Runtime.evaluate`) y captura la ventana con `Graphics.CopyFromScreen`. Ojo: el usuario tiene un segundo monitor a la izquierda con coordenadas **negativas**; localiza la ventana con `GetWindowRect` en vez de suponer la pantalla principal. Windows impide a un proceso en segundo plano robar el foco: para probar el Explorador al frente hay que simular Alt antes de `SetForegroundWindow`.

**Requisito para `cargo test`**: pdfium. Ejecuta una vez `powershell -File scripts/fetch-pdfium.ps1` (Windows) o `bash scripts/fetch-pdfium.sh` (Linux y macOS): descargan `chromium/8100` a `vendor/bin/pdfium`, ignorado por git, verificando el SHA-256 fijado en el script. Sin él fallan los tests de PDF, con un mensaje que lo indica; no se ignoran en silencio. Al subir de versión de pdfium, cambia `$Tag`/`$Sha256` en el `.ps1` y `TAG` y la tabla de hashes en el `.sh` (los hashes salen de la API de releases de GitHub: `assets[].digest`).

**Probar Linux desde Windows** (así se verificó, ver [docs/DISTRIBUCION.md](docs/DISTRIBUCION.md)): importa una distribución **desechable** con `wsl --import cvt-linux <carpeta en %TEMP%> <rootfs de Ubuntu 22.04>`, trabaja siempre con `wsl -d cvt-linux -u root -- bash <script>` (copia el código a `/root/converter` excluyendo `target`, `dist`, `vendor/bin` y `.git`; compilar sobre `/mnt/c` es lento) y al terminar `wsl --unregister cvt-linux`. **No uses ni toques las distribuciones que ya tenga el usuario** (`Ubuntu`, `docker-desktop`). Dentro hacen falta las dependencias de Tauri (README) y Rust con rustup; Node para `npx`. Los scripts largos se lanzan con `Start-Process wsl …` redirigiendo la salida a un archivo, sin comillas anidadas (pásalo como archivo `.sh`).

**CI** (`.github/workflows/`): `ci.yml` prueba en Windows, Ubuntu 22.04 y macOS; `release.yml` construye los paquetes de cada sistema y deja un borrador de release. Ejecutados en GitHub (CI en verde en los tres sistemas; release `v0.1.0` en éxito, como borrador; no hay `gh` en el equipo: se publica en la web). **Los fixtures de `tests/fixtures/` van marcados `-text` en `.gitattributes`: son datos, y con `core.autocrlf=true` Git cambiaba los saltos de línea de dentro de las celdas CSV y los tests fallaban solo en Windows.** Cuando consultes la API pública de GitHub, ten en cuenta el límite de 60 peticiones por hora. Una función o `use` que solo se usa en Windows falla `clippy -D warnings` en Linux/macOS: ponle `#[cfg(windows)]` (o `any(windows, test)`) y comprueba también en Linux.

Los fixtures de `crates/converter-core/tests/fixtures/` se generan con Pillow y `zipfile` (codificadores independientes de los crates del motor, para que los tests no sean circulares): `python -I crates/converter-core/tests/make_fixtures.py crates/converter-core/tests/fixtures`. Se versionan; el test `every_published_pair_converts_a_real_file` recorre todo el grafo y falla si se registra un par sin fixture de origen (añade el fixture en `sample()` de `tests/conversions.rs`).

**Tests con programas externos** (`tests/office.rs`): DOCX→TXT es Rust puro y corre siempre; lo que usa Word o LibreOffice va con `#[ignore = "motivo"]` porque automatizar Word en un `cargo test` normal puede tardar o colgarse. Se ejecutan a propósito con el comando de arriba (`word_*`, `wordcraft_*` y `libreoffice_*`; los de WordCraft necesitan `vendor/bin/wordcraft` —lo deja `scripts/build-wordcraft.ps1`— o `CONVERTER_WORDCRAFT`, tardan ~3 s en total y se pueden lanzar solos con `-- --ignored wordcraft`; para LibreOffice define `CONVERTER_LIBREOFFICE` con la ruta de `soffice.exe`; sirve una extracción administrativa `msiexec /a LibreOffice.msi /qn TARGETDIR=...`, que no instala nada). El test `engine_pairs_listed_here_are_exactly_the_ones_the_engine_offers` y la constante `ENGINE_PAIRS` (duplicada en `conversions.rs`) obligan a cubrir cualquier par nuevo que dependa de un motor externo. El instalador se compila con un `CARGO_TARGET_DIR` aparte para no bloquear el `target` de desarrollo; `tauri.bundle.conf.json` (con `resources` de pdfium) está separado de `tauri.conf.json` a propósito: `tauri-build` exige que existan los recursos, y eso rompería `cargo build` sin haber ejecutado `fetch-pdfium.ps1` y `build-wordcraft.ps1`.

Herramientas externas **no instaladas** en la máquina de desarrollo: Tesseract, ImageMagick, Pandoc, FFmpeg (LibreOffice tampoco: solo hay una copia extraída en el directorio temporal para probar). Sí hay Microsoft Word. Ningún test ni código del `core` debe asumir que existen en el `PATH`; si un conversor las necesita, debe detectarlas y degradar con un error claro (o los tests se marcan `#[ignore]` con motivo).

## Arquitectura

Workspace en `crates/`: `converter-core` (motor), `components` (descarga e instalación de componentes: **el único crate que abre conexiones de red**), `os-shell` (selección de archivos del gestor del SO) y `palette-app` (Tauri 2, binario `converter`). Regla estructural: **`converter-core` es una biblioteca pura, sin UI ni llamadas a Win32**, probable con `cargo test` sin entorno gráfico. Todo lo específico de cada SO (atajo global, leer la selección del Explorador/Finder/gestor de Linux, menú contextual, códecs nativos como WIC/ImageIO para escribir HEIC) y la UI viven en crates separados que dependen del core, nunca al revés.

Tres piezas del core que se entienden solo leyendo varios archivos:

1. **Grafo de conversión**. Los formatos son nodos y cada conversor es una arista con calidad (sin pérdida/con pérdida). `Engine::targets(from)` devuelve los destinos ordenados por **coherencia** con la tabla de probabilidades a priori de `ranking.rs` (JPG→WEBP/PNG sube; JPG→BMP baja), nunca ofrece el propio formato. Las conversiones entre familias existen solo donde un conversor las declara explícitamente (imagen→PDF, PDF→imagen/TXT); no hay reglas genéricas. La paleta solo consume esta lista; no decide nada por su cuenta. **Aún no implementado** (previsto en `docs/REQUERIMIENTOS.md` §4): rutas de varios saltos penalizadas, contadores de uso locales que reordenen el ranking y "combinar en PDF" con varias imágenes.
2. **Conversores**. Trait `Converter` con `supports(from, to) -> Option<Fidelity>` y `convert(&[u8], ...)`: trabajan sobre bytes, sin rutas. No hay tabla de pares: el `Engine` (`engine.rs`) pregunta a cada conversor registrado, y esa es la única fuente de qué se ofrece. Una conversión puede producir varias salidas (un PDF → una imagen por página): `Converter::convert_pages` entrega cada `Page { bytes, index, total }` a un `sink` según está lista, sin acumularlas en memoria, y `Engine::convert_file` devuelve `Vec<PathBuf>`. Con `total == 1` el archivo va junto al original; con más, a una carpeta nueva `<nombre>/<nombre>-N.ext` (`OutputSet` en `output.rs`, con relleno de ceros y rollback completo si algo falla a mitad). `Converter::convert` devuelve solo la primera salida. Un par entra solo si tiene test con archivo real. `Engine::convert_file` detecta el formato por contenido (la extensión solo desempata; un JPG renombrado a `.png` se convierte como JPG), deja el resultado junto al original sin sobrescribir (`foto.webp`, `foto (1).webp`...) y lo escribe de forma atómica (`output.rs`: reserva con `create_new`, temporal, renombrado; el manejador de la reserva debe cerrarse antes de renombrar porque Windows no reemplaza archivos abiertos). `ImageConverter` usa el crate `image`; `TabularConverter` pasa todo por una tabla intermedia, así cada formato de datos solo necesita lector y escritor.
3. **OCR como proveedor intercambiable**. Trait `OcrProvider` con `LocalTesseract` (por defecto; ejecuta el binario `tesseract` como proceso externo, descargado bajo demanda o el del sistema) y `RemoteService` (reservado). Sin bindings nativos de Tesseract. El OCR es **opt-in por conversión** (por defecto desactivado) y solo aplica cuando el destino es texto/documento. No acoples ningún conversor a un motor OCR concreto.

La paleta tiene 8 pétalos y **uno es siempre la tuerca de configuración** (inferior derecho, `SETTINGS_SLOT` = 3; el hueco que dejó el boceto). Nunca lleva un formato: no lo rellenes con uno. Antes estaba reservado para un servicio externo de pago (D-10); el usuario lo cambió por los ajustes (D-32), y cualquier cosa futura (cuentas, OCR, atajo) va dentro de ese panel.

**`os-shell`** (`selected_files()`): en Windows lee la selección con COM (`IShellWindows` → `IServiceProvider` → `IShellBrowser` → `IFolderView2::Items(SVGIO_SELECTION)`); según la clase de la ventana en primer plano usa el Explorador (`CabinetWClass`) o el Escritorio (`Progman`/`WorkerW`, vía `FindWindowSW`); otra ventana → `ShellError::NotAFileManager`. Con pestañas, varias entradas de `IShellWindows` comparten `HWND` (una por pestaña) y **hay que elegir la activa**: la visibilidad de la vista **no sirve** (una pestaña inactiva sigue «visible», y con la ventana minimizada ninguna lo parece; se midió en Windows 11 compilación 26300 y fue el error «no hay nada seleccionado» en el Explorador con varias pestañas, mientras que el Escritorio iba bien). La pestaña activa es la ventana hija `ShellTabWindowClass` que está **más arriba en el orden Z entre sus hermanas** (`tab_z_rank`/`choose_tab`, con tests); sin `ShellTabWindowClass` (Explorador sin pestañas) se cae a la visibilidad y luego a la primera. Si hay selección pero ningún elemento tiene ruta en disco («Inicio», Papelera), se devuelve un error que lo explica, no «nada seleccionado». **Para probar con pestañas reales**: abre una ventana de prueba, añade la pestaña con UI Automation (`AutomationId = AddButton`, `InvokePattern`), navégala con `Navigate2` por COM, selecciona con `Document.SelectItem(item, 0x1D)` y cambia de pestaña con `SelectionItemPattern.Select()` sobre el `TabItem`. **No uses `SendKeys`**: va a la ventana que tenga el foco (una vez fue el terminal del usuario). Cada llamada inicializa COM en su hilo (`ComGuard`). Verificado a mano con un Explorador real (2 archivos con ñ y espacios; 0 sin selección) y la consulta COM del Escritorio solo sin selección; la rama del Escritorio con archivos seleccionados **no está probada**. En macOS/Linux devuelve `Unsupported`.

**`palette-app`**: `palette.rs` es el modelo de vista puro y con tests (`build(files, engine) -> Payload`): rellena los pétalos 0,1,2,4,5,6,7 (arriba y en sentido horario, saltando el 3 reservado) en el orden de `Engine::targets`; con varios archivos ofrece solo los destinos comunes a todos; detecta el formato leyendo 64 bytes. `main.rs` crea la ventana (transparente, sin bordes, siempre visible, `visible: false`), registra el atajo, la bandeja y `tauri-plugin-single-instance` (una segunda ejecución con rutas reenvía los archivos a la instancia viva: es la base del menú contextual/"Enviar a"). La ventana se centra en el cursor acotada al monitor (`monitor_from_point`), se oculta al perder el foco o con Esc, y el atajo la alterna. El estado va al frontend por el evento `palette://open` **y** se guarda en `AppState.payload` para que la página lo pida con `current_palette` al cargar: sin eso, al arrancar con archivos el evento llega antes que el escuchador y la paleta sale vacía. La UI no ordena, filtra ni convierte: solo pinta y llama a `convert(format)`. El interruptor "con OCR" está deshabilitado hasta que exista el OCR.

Comportamientos del core que no son obvios y tienen test (no los cambies sin actualizar el test):
- PNG con transparencia → JPG se compone sobre **blanco** (no negro); el destino se marca `Fidelity::Lossy`.
- WEBP se escribe con libwebp (crate `webp`, C compilado y enlazado estáticamente: necesita compilador de C, no añade DLLs). `WebpMode::Auto`: desde JPG con pérdida (q80), desde PNG/BMP/TIFF/GIF sin pérdida; el límite del formato es 16383 px por lado y devuelve error, nunca `unwrap` (usa `encode_simple`, no `encode`). GIF/WEBP animados y TIFF multipágina convierten solo el primer fotograma/página.
- CSV: se detecta el separador (`;` de Excel en español), se acepta BOM y, si no es UTF-8 válido, se decodifica como Windows-1252. Un texto solo se convierte en número si es seguro (`007` y más de 15 dígitos se quedan como texto). La salida CSV lleva BOM UTF-8 y CRLF por defecto.
- **Orientación EXIF**: `decode_image` la aplica siempre (las fotos de móvil se guardan tumbadas con una etiqueta que los formatos de salida no conservan; sin esto salían rotadas). Los metadatos (EXIF, perfiles de color) no se conservan.
- **JPG truncado = error**: el decodificador de `image` es tolerante y devuelve una imagen parcial; `jpeg_is_complete` recorre los segmentos hasta el EOI y rechaza los cortados. No busca `FF D9` a ciegas (la miniatura EXIF lleva el suyo, y hay fotos con vídeo añadido tras el final).
- **Imagen → PDF** (`pdf_write.rs`, `pdf-writer`): una página A4 de 10 mm de margen, vertical u horizontal según la imagen, contenida y centrada. Un JPG RGB/gris sin giro EXIF pendiente se incrusta **byte a byte** (`DCTDecode`, no crece); el resto va con Flate y, si tiene transparencia, con máscara alfa (`SMask`). Siempre se decodifica antes para validar el archivo.
- **PDF → imagen/TXT** (`pdf.rs`, `pdfium-render`): destinos PNG, JPG, WEBP y TIFF (no BMP/GIF), 150 dpi por defecto (`ConvertOptions::pdf_dpi`, entre 36 y 600) y como máximo 10 000 px por lado. pdfium solo puede inicializarse una vez por proceso: hay una instancia global (`OnceLock` + `Mutex` de arranque) y la feature `thread_safe` serializa las llamadas. Se busca en `CONVERTER_PDFIUM_DIR`; donde deja cada paquete la biblioteca, medido en los paquetes reales (`packaged_pdfium_dirs`: `<exe>/pdfium` en Windows, `<exe>/../Resources/pdfium` en macOS, `<exe>/../lib/Converter/pdfium` en Linux —con la `C` mayúscula, es el `productName`—, y la carpeta del ejecutable); y, solo en compilaciones de depuración, en `vendor/bin/pdfium` del repo (ruta fijada con `CARGO_MANIFEST_DIR`); si no está, `Error::MissingDependency`. PDF → TXT devuelve UTF-8 con BOM y páginas separadas por línea en blanco; un PDF sin texto (escaneo) devuelve `Error::NeedsOcr`, que es el punto de enganche del OCR. PDF con contraseña se traduce a `Decode` (**sin fixture ni test**).
- **Documentos de Office** (`office.rs`), tres motores externos (D-41, D-44): **WordCraft** (`wordcraft-cli convert entrada salida`, Rust puro, 35 MB, viaja con la app), **LibreOffice** y **Word** (Windows; se detecta con el ProgID `Word.Application`). **La elección es por par de formatos** (`choose_engine`, pura y con tests): `Auto` y `WordCraft` usan WordCraft si sabe hacerlo (`wordcraft_supports`: DOCX/DOC/Markdown → PDF y DOC → DOCX) y está; si no (**PDF → DOCX**, que WordCraft no hace), LibreOffice y después Word; elegir LibreOffice o Word a mano los fuerza. Sin ninguno, `MissingDependency` (el nombre contiene «LibreOffice» cuando la paleta puede ofrecer descargarlo). `find_wordcraft` busca `CONVERTER_WORDCRAFT`, las carpetas de cada paquete (`packaged_wordcraft`: `<exe>/wordcraft`, `../Resources/wordcraft`, `../lib/Converter/wordcraft`) y, solo en depuración, `vendor/bin/wordcraft`; **no mira el `PATH`** (otra versión podría comportarse distinto). Se ejecuta con `WORDCRAFT_NO_PREFS=1` para que no escriba preferencias en el perfil. Se compila con `scripts/build-wordcraft.ps1`/`.sh` fijado a una **etiqueta y un commit** (v0.8.0): al subir de versión, cambia `$Tag`/`$Commit` (y `TAG`/`COMMIT`) y repite `cargo test -p converter-core --test office -- --ignored wordcraft`. Redistribuirlo exige llevar sus licencias (`vendor/bin/wordcraft/LICENSE-*`, `NOTICE`, `ATTRIBUTION.md`; ya van en los `resources`). Los motores trabajan sobre una carpeta temporal con nombres ASCII fijos (`input.docx` → `output.pdf`). Detalles de Word aprendidos a golpes (`word_convert.ps1`, ejecutado con `powershell -File`, sin ventana):
  - `Close`/`Quit` esperan argumentos por referencia: `$word.Quit($false)` falla y deja un `WINWORD.EXE` invisible; hay que usar `Quit([ref]$false)`.
  - El documento se abre de solo lectura con una **contraseña ficticia**: un documento protegido da error en vez de quedarse esperando un diálogo invisible. `AutomationSecurity = 3` desactiva las macros.
  - El script anuncia por stdout `WORD_PID=<n>` de cada proceso Word que crea; si no aparece uno nuevo, Word reutilizó **la instancia del usuario** y no se cierra. En un timeout (180 s) se matan el PowerShell y esos PID (`taskkill /T`).
  - **Guardar como `.doc` con Word oculto se cuelga** (PowerShell reintenta sin parar y dispara la CPU): por eso el motor solo guarda PDF y DOCX, y `Format::Doc` es solo origen. `make_doc_fixture.ps1` genera el fixture con Word visible.
  - PDF → DOCX usa el reflujo de PDF de Word (18 s para 3 páginas): aproximado; un escaneo sale como imágenes.
  LibreOffice: perfil propio por conversión (`-env:UserInstallation=file:///...` con porcentaje-codificación), `--infilter=writer_pdf_import` para abrir PDF en Writer (si no, abre Draw y no exporta a DOCX); cada llamada arranca un perfil nuevo (~20 s).
- **Motor preferido** (D-41/D-44, **sustituye a D-28**): WordCraft primero para lo que sabe hacer (el usuario lo pidió para no depender de LibreOffice y aligerar la app: 0,3–1,4 s frente a ~20 s). Medido: DOCX/DOC → PDF casi idéntico a LibreOffice; **Markdown → PDF** salía peor que con LibreOffice por el HTML (su importador de HTML de WordCraft **ignora los anchos de columna**: todas iguales), y se resolvió con D-47 (abajo); PDF → DOCX **no** lo hace. `CONVERTER_DOCUMENT_ENGINE=wordcraft|word|libreoffice` en la app, o el tercer argumento del ejemplo `convert`, fuerzan uno. Riesgo conocido: WordCraft es alfa y usa las fuentes del sistema (LibreOffice llevaba las suyas); no se ha fuzzeado.
- **Markdown → DOCX y → PDF con WordCraft** (`md_docx.rs`, D-47): Rust puro (`pulldown-cmark` + `zip`, sin dependencias nuevas). `MarkdownDocxConverter` publica el par Markdown → DOCX (siempre disponible, sin motor externo); `office.rs` lo reutiliza para imprimir con **WordCraft** (Markdown → DOCX → PDF), porque el importador de HTML de WordCraft ignora los anchos de columna, el sombreado de `th` solo lo respeta con `bgcolor` y el DOCX sí respeta anchos (`tblGrid`/`tcW`). **Los anchos se calculan por contenido** (`column_widths`: proporcional a los caracteres de la celda con tope de 120, mínimo = palabra más larga **topada en 14 caracteres** —una ruta sin espacios no debe aplastar a las columnas cortas— a ~135 vtw/carácter, y 63 columnas como máximo, el límite de Word). Hay cabecera sombreada y repetida (`tblHeader`), filas que no se parten (`cantSplit`), listas con `numId` propio y `startOverride` por cada lista numerada, enlaces como `w:hyperlink` con relación externa (solo http/https/mailto), y papel A4/Carta según el ajuste. **Seguro**: el HTML en bruto se reduce a su texto (`strip_html`: `<br>` → salto, `<img alt>` → `[imagen: alt]`, `<script>`/`<style>` y comentarios descartados, **también el texto que llega entre etiquetas en línea**), se quitan los caracteres de control (un `\u{0}` invalidaría el XML) y hay tests con entrada hostil. Con LibreOffice y Word se sigue imprimiendo el HTML de abajo.
- **Markdown → PDF con LibreOffice/Word** (`markdown.rs` + `office.rs`): `pulldown-cmark` genera un HTML autocontenido y **seguro** (el HTML en bruto se escapa, las imágenes nunca se descargan —salen como `[imagen: alt]`—, solo enlaces http/https/mailto) y el motor lo imprime. LibreOffice ignora los bordes de tabla del CSS pero respeta `border="1"`, y las fuentes de los títulos hay que fijarlas explícitamente; se revisó a ojo el PDF de ambos motores. Entrada con BOM o en Windows-1252 se decodifica como el CSV.
- **PDF → Markdown** (`pdf_markdown.rs`): heurística sobre cada carácter que da pdfium (tamaño, negrita, cursiva, monoespaciada, posición). Títulos por tamaño respecto al cuerpo (≥1,15×, ≥1,35×, ≥1,7×), párrafos por el espacio entre líneas, listas con viñeta o numeradas, bloques de código por fuente monoespaciada (con su sangría), palabras partidas con guion de fin de línea unidas, encabezados/pies/números de página repetidos descartados, párrafos que cruzan de página unidos. **pdfium devuelve el guion de fin de línea como el carácter de control U+0002 marcado con `is_hyphen()`**: hay que tratarlo como `-` (un test con datos sintéticos no lo habría detectado; lo cazó el PDF real). Limitaciones: no reconoce tablas ni imágenes; un escaneo devuelve `NeedsOcr`. Salida UTF-8 **sin** BOM.
- **Componentes bajo demanda** (`crates/components`): `install_libreoffice` descarga el MSI de LibreOffice (versión, URL, tamaño y SHA-256 fijados en el código), **reanuda** si se corta (`Range`, reintentos con espera creciente; un servidor que ignora `Range` reinicia limpio), verifica el hash, extrae con `msiexec /a` (extracción administrativa: sin instalar, sin administrador, sin tocar el registro) a `libreoffice-<versión>.partial` y solo entonces renombra; con un bloqueo `.install.lock` contra instalaciones simultáneas. Va en `components_dir()` (`%LOCALAPPDATA%\Converter\components`; `CONVERTER_COMPONENTS_DIR` lo cambia). `find_libreoffice` busca, en este orden: `CONVERTER_LIBREOFFICE` → **incluido en la app** (`<exe>/libreoffice`, `../Resources/...` en macOS) → descargado por la app → `Program Files` y rutas del sistema → `PATH`; descarta las carpetas `.partial`. La descarga es de 374 MB (decimales; 358 MiB). Completo ocupa 1,5 GB, así que **se poda** (`prune_libreoffice`, antes de renombrar `.partial`): quita diccionarios y extensiones (462 MB), idiomas de interfaz salvo es/en (262 MB), temas de iconos, galería, plantillas, asistentes, autotexto y ayuda; deja **690 MB** y las 5 conversiones siguen pasando con contenido real. **Nunca borres `readmes/`** (avisos de licencia MPL) ni `share/registry`. La poda se probó con LibreOffice 26.8.1; al subir de versión hay que repetir `libreoffice_converts_every_engine_pair_with_real_content` contra la copia podada.
  - `msiexec` solo acepta **rutas absolutas** (con una relativa da el 1619 "no se pudo abrir el paquete"): `install_libreoffice_into` las normaliza con `std::path::absolute`.
  - `cargo run -p components --example prepare_bundle -- <carpeta>` hace descarga + hash + extracción + poda (es lo que usa el instalador completo).
  - **Error 1603 de `msiexec` = ruta demasiado larga.** LibreOffice tiene rutas internas de hasta 100 caracteres; si la carpeta destino pasa de ~155, Windows Installer falla con un 1603 genérico. Se comprueba **antes** de descargar (`check_path_length`) y el error dice qué variable definir. Además se guarda `install.log` (`/L*v`) y se añade al mensaje la última línea de error. Un MSI ya descargado y con hash correcto se reutiliza.
  - macOS/Linux: `ComponentError::Unsupported` (no hay paquete fijado). **La app no ofrece descargar donde no se puede**: `components::libreoffice_installable()` (solo Windows x64) gobierna la oferta de la paleta y el botón «Instalar» de los ajustes (`SettingsView.can_install_libreoffice`), y `converter_core::libreoffice_install_hint()` da el texto por sistema (`sudo apt install libreoffice-writer`, `brew install --cask libreoffice`…) para el error y los ajustes. Los `.deb`/`.rpm` solo **recomiendan** `libreoffice-writer`.
- **Ajustes** (`settings.rs`, `get_settings`/`save_settings`/`pin_palette`): `Settings` se serializa a `settings.json` junto a la carpeta de componentes (`components_dir().with_file_name("settings.json")`), con escritura atómica; un archivo ausente, corrupto, con un valor desconocido o con cifras absurdas **nunca impide convertir** (vuelve a los valores por defecto y se acotan las cifras). `CONVERTER_DOCUMENT_ENGINE` manda sobre el ajuste. La interfaz guarda con un retardo de 250 ms al tocar un control y al cerrar el panel. **El panel usa botones segmentados y no `<select>`**: el menú nativo de un `<select>` le quita el foco a la ventana y la paleta se ocultaría; además, mientras el panel está abierto la paleta queda «fijada» (`pin_palette` suma al contador `busy`). `PdfPaper::{A4, Letter}` es una opción del core (`ConvertOptions::pdf_paper`; carta = 612×792 pt).
- **Mantenimiento y desinstalación** (panel de ajustes, sección «Mantenimiento»): `uninstall_libreoffice` quita **solo** lo que descargó la aplicación (`components::uninstall_libreoffice`: borra `libreoffice-*` e `install.log`, nunca otros componentes ni los ajustes, se niega con `Busy` si hay una instalación en curso y devuelve error si un archivo está en uso); no puede quitar el LibreOffice incluido (viaja en la carpeta de instalación y se va con el desinstalador) ni el del sistema. `uninstall_app` lanza `<instalación>/uninstall.exe` **desacoplado** (`DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`) y cierra la app 600 ms después para que pueda borrar el ejecutable; solo existe si se instaló con el instalador (`can_uninstall_app`). Ambos botones piden **confirmación en dos pasos** (el primer clic arma 4 s). La comprobación «hay una operación en curso» (`operations_running`) descuenta la fijación del panel, que también suma a `busy`.
- **Desinstalador de Windows** (`crates/palette-app/nsis-hooks.nsh`, `installerHooks` en los dos `tauri.bundle*.conf.json`): el macro `NSIS_HOOK_POSTUNINSTALL` borra `%LOCALAPPDATA%\Converter\components` (LibreOffice descargado, ~700 MB que antes quedaban huérfanos) salvo en una actualización (`$UpdateMode = 1`); con la casilla «borrar datos» (`$DeleteAppDataCheckboxState = 1`) borra también los ajustes; si la carpeta queda vacía, la retira. **Cómo se probó sin tocar datos reales**: se compila con `makensis` un mini-instalador que incluye **el mismo texto del gancho** con `$LOCALAPPDATA` sustituido por una variable de prueba y se ejecutan los 5 casos contra carpetas desechables. **No se ha ejecutado el desinstalador real de punta a punta** (ni la rama de la casilla en la interfaz del desinstalador).
- **Flujo en la paleta**: si una conversión falla con `MissingDependency` de LibreOffice, `Outcome.needs` lleva una `Offer` y la interfaz muestra "Descargar / Ahora no"; al aceptar, `install_component` emite `component://progress` (descargando → verificando → instalando) y, al terminar, **reintenta sola la conversión pendiente**. La bandeja tiene "Instalar LibreOffice…". `AppState.busy` (contador + `BusyGuard`) evita que la paleta se oculte al perder el foco mientras convierte o descarga.
- **DOCX → TXT** (`docx_text.rs`): `zip` + `roxmltree` (DTD prohibido, tope de nodos y de bytes descomprimidos). Párrafos, tabulaciones, saltos y tablas (celdas con tabulador, filas con salto); no incluye notas, encabezados ni pies. UTF-8 con BOM y CRLF.
- XLSX → otros: solo la primera hoja; se conservan valores, no fórmulas ni estilos. JSON debe ser un arreglo de objetos.
- `Format::sniff` exige 4 bytes reservados a cero tras `BM` para no confundir un CSV que empieza por "BM" con un BMP.

## Restricciones del proyecto

- Sin red, sin cuentas y sin telemetría en el core; debe funcionar 100 % offline. El servicio externo con suscripción es visión futura, no se implementa ahora.
- Prohibido enlazar GPL (p. ej. x265): HEIC se lee con libheif (LGPL, solo enlace dinámico) y se escribe con códecs nativos del SO; no hay escritura de HEIC en Linux.
- Rust no cubre bien algunos casos y la dependencia nativa elegida condiciona la distribución: DOCX→PDF fiel (Word o LibreOffice bajo demanda), PDF→imagen (pdfium, **empaquetado**: `bundle.resources` lo instala en `<instalación>/pdfium/pdfium.dll`, que es `exe_dir/pdfium`, una de las rutas que busca el core). Binarios pesados (LibreOffice, Tesseract) se descargan bajo demanda con hash verificado, nunca en el instalador base. Antes de añadir otra dependencia nativa, confirma con el usuario porque cambia el instalador y la licencia.
- Errores del core como tipos (`thiserror`), sin `panic!` ante entradas malformadas.
